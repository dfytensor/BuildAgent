# 格物致知 — 用 150 个阶梯用例把一个 1B 模型调教成数据分析 Agent 的完整过程(去作弊泛化版)

> 目标模型: MiniCPM5-1B (cpm5-1b-bf16xl, 未做任何微调, max-ctx 8192, ixrun step-graph 推理服务)
> 方法名: **格物致知** — 先"格物"(测定模型与任务的客观边界), 再"致知"(每轮迭代只解决测量出的缺陷), 用同一把尺子(150 用例)度量每一轮的能力增量。
> **诚实结论**: 去除一切对着题库设计的机制后(v7_general), 工具调用成功率 **0% → 90.7%**, 结果可执行率 **0% → 16.7%**, 最终答对率 **2% → 8.7%**(pandas 套件 20%, 图表题 8/10 且经"当轮生成"校验)。
> **1B 的真实画像**: 工具协议可以通过工程脚手架教会(90%+); 但 SQL/代码的**语义正确率是未微调小模型的天花板**, 多轮自由问答场景弱(端到端 7 轮 demo 中图表类成功、自由 SQL 类多数诚实失败)。此前 v6 报出的 14% 中约 9 分来自模板/正则工程, 已剥离并单列为"工程能力", 不再计入模型能力。

> **闭环状态(2026-10-25)**: 同尺 150 题已完成五模型对照。
> **v1.1 修正评测**: deepseek-flash + v11d **99.3%(149/150)** · spark-x2.6-4b(本地) + v11d **76.7%(115/150)**。
> **v1.0 冻结评测(官方阶梯)**: 1B 25% → 2B 32% → spark-4B(v9) 56.7% → spark-4B(v11c) 65.3% → minimax(v9) 67.3% → deepseek(v11c) 86.0%。
> **机制账本**: 脚手架(v11a-v11d)与评测(v1.1)分列; 单臂误差棒 ±2.8pt(1σ); 失败解剖见 §2.5.9。

### 0.3 150 个阶梯评测用例 (eval/build_cases.py → cases.json + 黄金答案)
- **SQL 50 题(L1-L9)**: 单表单字段 → 单表多字段 → 单条件 → 多条件 → 多表 → 多表多条件聚合(销售额/GROUP BY/TOP-N)
- **pandas 50 题(P1-P4)**: 单算子 → 双算子 → 多算子多步 → **出图 10 题**(校验 PNG 真实落盘)
- **工具调用 50 题(T1-T6)**: 一轮一次 → 一轮多次 → 多轮每轮一次 → 相隔几轮引用 → 连续多跳依赖 → **跨 maxlen 依赖**(6-9 轮长对话后引用最早轮数值)

每题黄金答案由参考实现(SQL/pandas)预计算, 自动判分。**提示词/few-shot 与题面做过去重**: v3 曾发现示例题与 SQL-L3-01 撞车, 修复后全量重跑。

### 0.4 判分指标 (eval/checker.py)
- **工具OK**: 调用次数 ≥ 题目要求
- **执行OK**: 次数达标 且 全部执行无错误
- **最终答对**: 末轮答案含全部黄金标量(数值容差 0.5%/0.01, 字符串包含)
- **图表题(加固后)**: 文件存在 + 大小达标 + **mtime ≥ 本用例开始时间**(杜绝跨轮残留文件假阳性)

## 2. 端到端最终验证 (eval/final_demo.py, v7_general 诚实跑)

7 轮商业分析会话(总览→趋势→出图→品类→区域对比→压力填充→跨轮引用), **不使用任何模板/正则兜底**:

- **成功**: 轮3 出图(模型填槽→校验→make_chart 落盘 chart_demo_01.png, 1.8s) — 受约束接口路径稳定可靠。
- **诚实失败**: 轮1/2/4/7 自由 SQL 语义错误(`YEAR()` 方言幻觉、缺 GROUP BY、幻觉列名)全部以"查询失败+原因"呈现, **无一例编造数字**; 轮5/7 规划器拒绝调用时明确告知无法回答。
- 全程 trace/图表/事实卡落盘, 可审计。

**这就是去作弊后 1B 的真实画像**: 受约束接口(填槽)可靠, 自由语义生成不可靠但失败诚实。生产系统的正确姿势是: 把高频路径产品化为约束接口(标注为工程能力), 把长尾交给模型并接受其失败率, 或对失败启用人工/更大模型兜底。

## 2.5 能力地形图: 问题难度 × 轮数深度 (数据: eval/difficulty_gradient.py → difficulty_turn_gradient.json)

三条阶梯(SQL L1-L9 难度 / pandas P1-P4 算子数 / tool T1-T6 轮数×依赖) × 三层指标(协议/落地/语义) × 8 个版本:

| L6 多表 | 100% | 0% | 0% | | T6 跨maxlen(6-9轮) | 100% | 0% | 0% |

### 关键发现: 分界线不是"难度", 是"语义自由度"
1. **难度阶梯预言不了 1B 的失败位置**: 语义悬崖不在 L9 高级聚合处, 而在 **L1 就塌了**(17%), L2-L9 全零——方言错误/列名幻觉/漏 GROUP BY 在所有难度层随机发生。人类设计的难度阶梯对 1B 失败模式几乎没有预测力。
2. **协议层全地形拉满**: 工具OK 在全部 20 个层级(3 阶梯×所有层)保持 71-100%, 且不随难度/轮数衰减——8 轮迭代把"调用"彻底教会了。
3. **唯一被迭代推开的格子**: pandas P4 出图 0%(v0-v4) → 20%(v5) → 100%(v6,含正则兜底) → **80%(v7, 纯模型填槽+校验)**。它是唯一把语义自由度压成"填空"的路径。
4. **自由语义生成(SQL/代码)从 v0 到 v7 始终是悬崖**: 8 轮迭代没能把 L2-L9/T2-T6 的语义答对率推出 0% 附近(±17% 为 5-6 题小样本噪声)。要多跳正确, 要么每步约束成填槽, 要么微调/换更大模型。

> 设计启示: 对 1B 级模型, 多轮数据分析的可行路径不是"相信它连对三次", 而是**把每一步都压进受约束接口**(如 make_chart 的填槽模式, 其答对率不随轮数衰减), 或由代码代行多跳编排(每跳用模板/视图降低语义自由度)。

### 2.5.1 负收益记录: 确定性算术执行器救不了跨轮(v8_calculator)

**假设**: 跨轮失败源于"数值召回了但 1B 心算不可靠"→ 加 calculator 工具(模型从事实卡抄数值组装表达式, 代码 AST 白名单求值; 通用能力, 非题库模板)应救活 T4/T6。

**测量(v8 vs v7, tool 套件)**: 60%/14%/2% vs 80%/10%/4% — 无改善(T4 工具OK 100%→50%, 噪声级回归)。

**归因**: 跨轮的失败发生在**算术之前**——前置跳 SQL 语义错误(幻觉表名/错引 order_items 行数)、事实召回错位, 导致计算器拿不到正确输入。乘性衰减的第一因子在"每跳 SQL 语义", 不在"最后一步算术"。

**结论(能力边界陈述)**: 未微调 1B 的跨轮语义正确率是多跳乘积, 无法靠调用侧工程修复; 突破路径只剩 SQL 语义微调或更大模型。此为负收益, 依法记账。

### 2.5.2 部署对照: 同一 v7, 量化服务 vs bf16 修复服务(同尺 150 题)

| v7_general | 工具OK | 执行OK | 最终答对 | 全程答对 | SQL执行 | pandas执行 |
|---|---|---|---|---|---|---|
| 量化服务(bf16xl, 早期) | 90.7% | 16.7% | 8.7% | 10.0% | 2% | 8% |
| **bf16 修复版(minicpm5, B=8并发)** | 84.7% | **46.0%** | **14.7%** | **18.7%** | **58%** | **56%** |

- **执行率近 3 倍**(16.7%→46%), 最终答对 +6pt——此前把大量"语义失败"归给模型, 复测证明其中相当部分是**推理服务缺陷**(丢首 token/空答/20% 损伤率)导致 SQL/代码被截断损坏。
- **难度悬崖显著后退**: SQL L9 多表聚合执行率 0%→**80%**, L1-L9 全层执行 33-100%; P4 出图 80%→维持; T1 答对 20%→40%, T6 跨 maxlen 执行 0%→43%。
- **多轮规划仍脆弱**: T3 规划器崩(工具OK 12%), demo 中跨轮自由 SQL 仍出现错引(答"0"/幻觉"50%")——跨轮语义边界结论不变, 但边界位置比此前测得乐观。
- **方法论补丁**: 部署本身是被测系统的一部分——**换部署必须全量复测**, 否则会把服务缺陷误诊为模型缺陷(v7 量化版测量即此误)。

### 2.5.5 逐题四象限重叠分析(eval/overlap.py): 通往任意定制化 Agent 的核心理论

对两份同尺逐题结果做正确-错误四象限分解(演示对: v6@量化1B+模板 vs v7@2B 净脚手架, 混杂变量仅作工具演示):

| 象限 | 占比 | 语义 | 处置 |
|---|---|---|---|
| 双对 | 11% | 两代配置都覆盖 | 脚手架冗余可削减 |
| **双错(稳定超界区)** | **65%** | 与模型规模/版本无关的硬边界 | 三选一: 约束化(填槽)/模板化(标注工程分)/微调 |
| B独对(解锁区) | 21% | 新配置解锁, 集中在**低自由度单跳**(pandas P1/P2、SQL L1/L3/L4、T1) | 保留杠杆, 是能力增长区 |
| A独对(退化区) | 3% | 掩码依赖题(few-shot撞车题L3-01在列!)+单次抖动 | 审查, 用k次重复判稳 |

**三个核心洞察**:
1. **重叠是主体**(双对+双错=76%): 说明尺子在测量"模型×脚手架"的稳定能力, 而非噪声; 65% 双错区就是当前的**真实能力边界地图**。
2. **规模解锁的不是新任务种类, 是语义阈值**: 解锁区 31 题全部是"单跳语义抽签刚好过线"的题——模型升级移动的是**语义正确率阈值线**, 阈值线以下的自由生成题(高难度/多跳)两代全错。
3. **四象限=机制选择的决策树**: 双错稳定→约束化优先(工程分, 可靠), 微调其次(模型分, 贵); 解锁区→保杠杆; 退化区→查掩码/查抖动。

**任意定制化 Agent 的通用流程(从本实验抽象)**:
```
给定目标域:
1. 造尺: 域内阶梯用例+黄金答案(可机判) → 裸模型基线(四象限全错=正常)
2. 迭代: 单变量机制注入, 每轮全量复测+归档(archive) → 协议层打满为止
3. 差分: 换模型/换部署/改机制 → 重跑同尺 → 四象限+层级分布 → 定位解锁区/超界区/退化区
4. 分派: 双错稳定区 → 约束化/模板化/微调三选一(按可靠性-成本权衡, 并在账本中单列工程分)
5. 追踪: 模型升级时重跑同尺 → 解锁区自动扩大, 脚手架杠杆自动兑现; 不变项=下一轮靶子
```
此流程与域、模型、部署均解耦——**"任意定制化"的本质是: 尺子固定, 在(模型×部署×脚手架)三维空间里做带归因的坐标搜索, 四象限重叠分析就是搜索的梯度**。

数据管理教训: 1B(bf16) 逐题结果未归档被覆盖, 逐题级重叠分析被迫用混杂对演示——**runner 已加自动归档**(eval/results/archive/模型_时间戳), 此后任何两次运行都可做严格的同尺四象限。待 1B 服务恢复后重跑归档, 即可产出干净的 1B-vs-2B 逐题重叠地图。

**干净版已产出(10/22, 1B@8020修复后 vs 2B, 16 个代表用例)**: 双对 25% / 双错 38% / **2B独对(规模解锁) 38%** / **1B独对(退化) 0%**。解锁区 = PY-P2-09、SQL-L1-03、SQL-L3-02、SQL-L9-02、TOOL-T1-05、TOOL-T1-09; **零退化**——同尺差分在健康部署上给出了干净的规模对照。全量 150 题逐题重叠待 1B 服务长窗口运行(约 12-14 小时, 断点续跑就绪)。

### 2.5.6 部署指纹(二): 思考模型在 llama.cpp 上的预算陷阱与"答案路径关思考"原则

同一 4B 模型换部署(spark-x2.6-4b-lossless, GGUF/llama.cpp @8080)后, 18 题代表集首测 50%, 逐题审计发现 **"(回答失败)"全部不是网络异常**——`llama.cpp` 系服务里 `max_tokens` 同时约束 `reasoning_content` + `content`; 思考模型在特定提示(多行工具结果+规则复述)上会进入**病态反思维循环**, 把 700/2000/3000/4500 预算全部烧在思考上, 正文永远不开始。

**判别签名**: HTTP 200 + `content=''` + `usage.completion_tokens == max_tokens` + `reasoning_content` 非空。与"服务端空答损伤"(20% 随机)和 429 限流完全不同——它是**确定性的提示×模型组合病态**, 同一 prompt 每次必现。

**架构级修法(问题无关, 非作弊)**: 思考姿态由 micro-task 决定——
- 规划器(选工具/多跳): 保持思考 ON(原生 tool_calls 路径, 思考短且有效)
- **回答器/闲聊兜底/收尾(chat() 路径): 思考 OFF**(`chat_template_kwargs: {enable_thinking: false}`), 它只做"从观测抄数+按规则排版", 不需要推理

**修复效果(同一 18 题代表集)**: SQL 3/6 → **6/6**(L5-02/L9-02 从"答败"直接转对), 总 50% → **77.8%**(14/18)。L9-02 复现: 思考 ON 下 3000/4500 预算均空答(35s/52s 全烧思考); 思考 OFF 下 **2.2s/136 tokens 干净 FINAL, 六类目销售额全对**。

**全量 150 验证(10/24, 修复后)**: **56.7%(85/150), 基建标记 0**(无回答失败/无worker崩溃/无空答), 工具OK 97.3% / 执行OK 79.3%。四模型同尺阶梯就此定格: **1B 25% → 2B 32% → spark-4B(本地) 56.7% → minimax-m3.1 67.3%**; 4B 与大模型差 10.6pt, 主要缺口在 TOOL-L5 多跳(14%)与 SQL 中高层的粒度/连接类语义。

**思考姿态消融(全量 150, 同脚手架同预算 3000, 唯一变量=chat() 思考开关)**: 答案器思考 OFF **56.7%** vs ON **49.3%**。四象限: 双对 47%(70) / 双错 41%(61) / **OFF独对 10%(15题)** / **ON独对 3%(4题: SQL-L2-01/03/06 + PY-P2-07)**。ON 臂 **39 题(26%)触发答败签名**(200+空content+usage=预算上限), OFF 臂 0 题——**答案器思考不是"少赚", 是净亏 7.4pt**; 其微弱收益(单跳 SQL 类型判断)已被规划器思考覆盖。ON 臂执行率略高(82.0% vs 79.3%)但规划器两臂同配置, 属逐题抖动/批调度方差, 不构成思考收益证据。

**本轮新增的部署陷阱清单(与 2.5.2 合并为"部署指纹"体系)**:

| 陷阱 | 表征 | 判别 | 修法 |
|---|---|---|---|
| 服务端空答损伤 | ~20% 随机空 content | 同 prompt 重试可恢复 | 修部署(bf16 修复版) |
| 429 双形态(OpenRouter) | `free-models-per-day` vs `temporarily rate-limited upstream` | 看 error.metadata.raw 原文 | 前者等 UTC 日切/充值, 后者换时段/换模型 |
| key 限额 ≠ 账号日配额 | auth/key 显示 50/50 剩余, 免费模型仍 429 | 429 不计 key 限额 | 以实际 429 文案为准 |
| 思考预算截断/死循环 | 200 + 空 content + usage=预算上限 | 关思考复测即出答案 | 答案路径关思考; 规划路径保持思考 |
| worker"崩溃" | runner 报 `(worker崩溃)` | 单题裸跑正常 = 非崩溃 | 6×25s 退避 × 多调用 > 900s 断头台; stderr 落盘+单题裸跑复核 |

**方法论补丁**: 部署指纹不止"损伤率"一种形态。**思考模型的"预算→内容"关系是部署契约的一部分**——同一模型同一脚手架, 换服务(自研 batched vs llama.cpp GGUF)会换一类失败模式。测量前先做"思考姿态×预算"的二分探针, 再做逐题跑批。

### 2.5.7 机制消融: v10 语义层(query_metric)的真实增量 = +8.7pt

**实验设计(单变量)**: A 臂=有语义层(56.7%, 归档 102211) vs B 臂=从 TOOLS_SPEC + PLANNER_SYS 移除 query_metric(48.0%, 归档 145801); 同脚手架、同思考姿态(答案器关)、同预算 3000。**隔离性验证**: B 臂 150 份 trace 中 query_metric 调用 = 0——模型确实看不到该工具了。

| 指标 | A(语义层ON) | B(语义层OFF) | 差 |
|---|---|---|---|
| 最终答对 | **56.7%**(85) | 48.0%(72) | **+8.7pt** |
| 工具OK / 执行OK | 97.3% / 79.3% | 98.0% / 75.3% | +0 / +4.0 |
| SQL / pandas / tool | 48 / 58 / 64 | 44 / 54 / 46 | +4 / +4 / **+18** |

**四象限**: 双对 44%(66) / 双错 39%(59) / **语义层独对 19(13%)** / **语义层独错 6(4%)**——净 +13 题。独对集中在 TOOL-T2/T3/T6 口径题(销售额/订单量/商品款数)与 SQL-L8/L9、PY-L3; 独错 6 题(PY-P2-07, SQL-L4-04/L5-04/L9-04, TOOL-T1-10/T4-08)是"裸 SQL 本可写对、被语义层固定口径挤掉"的刚性成本。

**结论**: 对小模型, **"口径沉入代码"是当前 ROI 最高的机制之一**(+8.7pt, 零微调成本, 工具套件 +18pt 的主要来源); 但语义层不是免费午餐——刚性口径会在少数题上反噬, 下一版可做"metric 不适用时回退裸 SQL"的路由。同模型三姿态全量对照就此完整: **思考OFF+语义层 56.7% > 思考ON+语义层 49.3% > 思考OFF+无语义层 48.0%**。

### 2.5.8 误差棒与 v11 机制轮次账本(单变量逐轮)

**先量噪声, 再谈机制**(k=3 方差基线, 22 题分层抽样, 同配置连跑三遍):
- 三遍总分 16/14/14 → 均值 14.67/22, **逐题翻转率 14%** → **150 题总分标准差 ≈ ±4.2 题 = ±2.8pt(1σ)**
- 工具OK/执行OK 三遍完全一致(95.5%/81.8%)——**执行层稳定, 语义判定才是抖动的来源**
- 推论: 任何单臂全量对比, 净差 < ~6pt(2σ) 不能称为机制收益; 逐题"修好/弄坏"各 9-10 题正是 150×14%≈21 次翻转的期望值

| 轮次 | 机制 | 全量结果 | 类别级效果 | 判定 |
|---|---|---|---|---|
| v11a | 结果呈现层: 列名+全量行替代裸JSON截断(2400→6000字符) | 85/150=56.7% | **信息缺失类 4→1**; 9修好/9弄坏 | 总分在噪声内; 定向修复成立 |
| v11b | 空结果诊断: year/month/day TEXT 知识 + 四步诊断清单 | 85/150=56.7% | **空结果类 4→2, 信息缺失 0**; 10修好/10弄坏 | 同上; 两轮均零基建标记 |
| v11c | 语义层 v2: 实体级 `grain`+`top` 排名、`completed_order_count`、metric 优先于自写SQL、dim标签bug修复 | **98/150=65.3%** | **净+13题(超2σ)**: SQL-L9 5/5、TOOL-L6 7/7、pandas-L3 27→67%、T5 14→29%; 20修好/7弄坏 | **机制收益成立**; vs minimax 双错区 36→27 |
| deepseek | 官方API(V4.1-1017, deepseek-flash) + v11c 脚手架: 思考常开(reasoning_tokens 计费但收敛快)、答案器预算6000、空答重试、摘要器 make_chart rows(int) 修复 | **129/150=86.0%** | SQL 88 / pandas 90 / tool 80; 零基建标记 | **新台阶**: 同脚手架比 4B 本地高20.7pt; 与 minimax 双错仅13题; 剩余TOOL-T5多跳4题+SQL高难度6题 |

**v11 过程中发现并修掉的三个实现级陷阱(全部问题无关)**:
1. **派生数字是 4B 的毒药**: 摘要器加的 `行数:1` 被当成答案(COUNT题答"1"), `min/max` 被拿去乱算("20-1=119") → 呈现层只给列名+原始行, 不给任何派生数字。
2. **列表完整性必须显式要求**: 否则 13 行结果只列第一行 → ANSWER_SYS 增加"多行列表必须逐行完整列出, 以最后一条完整列表为准"。
3. **`query_metric` 的 dim 分组从未 SELECT 维度列**(声明了 label 列却只查聚合值)——v10 遗留 bug, 导致所有"按月/按类目"指标题丢标签; 修复后 `month` 直接返回 `2024-01` 格式, 与黄金对齐。另加"metric 结果优先于自写SQL"规则, 防止模型用错SQL覆盖正确口径。

**第四个陷阱(DeepSeek 轮暴露)**: `tool_make_chart` 返回的 `rows` 是**整数**(图的行数), 摘要器却按列表切片 `rows[:50]` → 回答器消息构造抛 `TypeError` → 该题直接 `(回答失败)`。触发条件是"模型在数据路径里顺手画图"(deepseek 在 L9-01/L9-04/T3-06 等 5 题触发)。修复: rows 非列表按空处理 + `summarize_result` 全函数异常兜底(呈现层永远不许抛异常); 修复后 5 题 **5/5 全过**。**教训: 任何进入回答器消息构造的代码都必须零异常——工具返回类型的多样性比想象中大。**

**DeepSeek 部署指纹**: 官方API(deepseek-flash/V4.1-1017): 思考常开且 `reasoning_tokens` 计入 completion 预算(探测显示收敛快, 0.7-1.3s/次); 高数字密度提示(12个月核对等)下偶发**瞬时空答**(HTTP 200 + content='' + finish=length), 需 ①答案器预算 6000(ANSWER_TOK/LLM_TOK_CAP) ②空答重试("直接输出FINAL, 不要重复分析") ③同一提示直连复现正常 → 判定为服务端瞬态而非提示病态。

### 2.5.9 "为什么强模型也到不了 100%": 21 道失败的解剖与三阶段修复

deepseek-flash + v11c 在 v1.0 评测上 86.0%(129/150), 21 道失败逐题解剖后**只有约 4 道是模型真错**:

| 失败成分 | 题数 | 典型证据 |
|---|---|---|
| **评测缺陷** | 8 | PY-P3-11 黄金恒 100%(分母子查询带 channel 过滤); SQL-L6-04/L7-01/L7-02 的 ref_sql **无 ORDER BY + LIMIT 15** → 黄金是任意 15 行; 4 题歧义(均价=售价/成交价、件=款/件数、明细行数=行数/件数、quantity 列无表名) |
| **口径分歧** | 6 | 黄金对"买过/购买件数/原价销售额"用全状态, 模型被"销售额只算 completed"提示过度泛化, 全按 completed 算 |
| **脚手架组装/跨轮** | 5 | 事实卡存的是"最后一次工具结果前120字"(T4-02 第1轮只存了 [[500]], 112 丢失); "以最后一条结果为准"让 L4-01 只列了 6/20; calculator 已算出 22.4 却被回答器说"无法计算" |
| **真能力/排序** | 1-2 | L6-02 按商品名序而非 id 序 |
| **采样抖动** | 2-4 | k=3 翻转率 14% → ±2.8pt |

**三阶段修复(每一阶段单变量)**:
1. **v11d 脚手架(+6.0pt → 92.0%)**: 事实卡改存"问答对"(答案里的数字得以跨轮保留) + 状态口径分层(历史购买=全状态, 销售额=completed) + 结果选择规则(最完整优先, calculator 结果必用) + `query_metric status='all'`。12 修好/3 弄坏。
2. **v1.1 评测修正(+7.3pt → 99.3%)**: 1 个黄金 bug + 3 题补 `ORDER BY` + 9 题去歧义。**不碰脚手架、不放宽判分**。
3. **残余 1 题(PY-P2-07)**: 题面已指定 order_items 表, 模型仍用 v_sales 的 45208/15988=2.83(正确 43899/14679=2.99)——**真错**, 保留。

**结论**: 强模型的"最后一公里"通常不是智力问题, 而是**评测质量 + 上下文工程**。在 v1.0 这套未修正的评测上, **100% 在原理上不可达**(8 道题没有唯一正确答案); 修正后 DeepSeek 达到 149/150。同时保留 v1.0 冻结分作为官方阶梯(v1.1 单列), 防止"改题抬分"污染历史对照——**改题必须全模型复跑, 且新旧两套分数并列**。

**4B 同轮验证(v11d + v1.1)**: spark 65.3% → **76.7%(115/150)**, 零基建标记。分解: **13 道修正题 1/13→9/13(+8, 评测账)**; **137 道未改题 97→106(+9, 脚手架账)**。与 deepseek(v1.1) 四象限: 双对 115 / **双错 1**(PY-P2-07) / **仅spark 0** / **仅deepseek 34**——4B 在修正后的评测上**没有一道 DeepSeek 不会的题**, 剩余 34 题是纯能力差距(SQL 中高层语义、T3-T5 多跳、P3 多步)。**评测/脚手架账占 4B 全部 35 道失败的 49%, 但 4B 的天花板仍是语义能力本身**——脚手架只负责把"本来会做的"兑现, 不会把"不会的"变成会。

## 3. 格物致知: 定制化 Agent 的核心步骤(方法论沉淀)



### 第一步: 格物 —— 先测边界, 再动手
1. **造确定性的物**: 固定 seed 的业务数据 + 参考实现, 让"对错"可机判。
2. **造阶梯式的尺**: 复杂度分层用例(150 题), 覆盖单轮/多轮/依赖/长上下文。
3. **裸模型基线必须先跑**: v0 把"模型缺什么"从猜测变成清单。

### 第二步: 致知 —— 单变量迭代, 一轮只治一个病
4. **每轮引入恰好一个机制**, 全量用例复测, 增量归因。
5. **允许负收益并记录**: v2 的 26%→0% 是最重要的一课 —— 小模型注意力是多约束零和博弈。
6. **证据链完整**: 每个缺陷都有 trace 原文作证。

### 第三步: 反作弊审查 —— 区分"教会"与"代考"
7. **三条红线**: ①提示词/few-shot 不得与评测题撞车; ②不得针对评测题面写正则/模板直答; ③判分不得依赖会话外的残留状态。
8. **归因账本**: 每一分都要能回答"这是模型会的, 还是工程代做的"。v6 的 14% 拆账后: 模型真实贡献约 5 分, 模板约 2-3 分, 图表管线约 7 分。
9. **泛化性检验标准**: 一个机制若只在评测题面成立、换个问法即失效, 即为助考; 若在任何同域问题上成立(词表归一、方言提示、白名单校验), 则为合法工程。

### 第四步: 致良知 —— 判断权从模型向代码有序转移(但要记账)
10. **模型只做填空**: 路由、槽位校验、文件名等 I/O 细节由代码接管; 模型失败时诚实报告, 不给幻觉。
11. **失败路径层层兜底, 兜底也记账**: 工程兜底提高系统可用性, 但在能力报告里必须与模型能力分开列示。

### 一句话总结
> **格物(阶梯用例测边界) → 致知(单变量迭代记账) → 反作弊(区分教会与代考, 泛化性一票否决) → 致良知(判断权移交代码并单列工程分)。**
> 去作弊后的最终答案: 未微调 1B + 问题无关脚手架 = **可靠的工具协议(90.7%) + 诚实的失败(不编造) + 受约束接口上的可用分析(图表/聚合)**; 自由语义生成仍是小模型天花板, 需微调或更大模型突破。

## 5. 已知边界(诚实声明)
- 未微调 1B 的语义天花板: v7 执行率 16.7% 意味着大多数自由生成的 SQL 语义有误; 系统以"查询失败+原因"呈现, 不编造。
- 服务端批处理非确定性: 同 prompt 偶有不同输出, 单题有抖动, 150 题聚合梯度方向稳定。
- 沙盒为演示级(静态黑名单+子进程超时), 生产需容器级隔离。
- 判分的子串匹配存在少量误报可能(如答案文本恰好含类目名), 各版本一致, 不影响梯度方向。
- **单题抖动已量化**: k=3 分层抽样翻转率 14% → 150 题总分标准差 ±2.8pt(1σ); 单臂对比净差 <6pt 不应称为机制收益(见 §2.5.8)。
- **PY-P1-02 题面歧义(已在 v1.1 修正)**: "商品的平均价格"可读作 products.price 均值(1592.71)或成交价均值(1507.16); v1.0 冻结不改, v1.1 已澄清为"商品表 price 列均值", 新旧两套分数并列记录。
- **v1.1 评测修正清单**: 黄金 bug 1(PY-P3-11) + 补 ORDER BY 3(SQL-L6-04/L7-01/L7-02) + 去歧义 10(PY-P1-02/P1-04/P2-02/P2-07/P2-13/P3-15、TOOL-T2-03/T4-03/T5-04 等); 备份 `eval/cases.v1.0.bak.json`。
- **DeepSeek 部署边界**: 思考常开且 reasoning_tokens 计入 completion; 高数字密度提示偶发瞬时空答(HTTP 200+空content), 需答案器预算6000+空答重试; 摘要器对工具返回类型(int rows 等)必须零异常兜底(已修)。
